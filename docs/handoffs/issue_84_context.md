# Issue #84: Add DELETE Endpoint for Task Attachments

## Business Value

**Who:** End users of KanbAI (project owners and project members) who have uploaded files to tasks and later need to remove them due to mistakes, obsolete content, or storage management requirements.

**What:** Provide an API endpoint that allows users to delete attachments they or their teammates have uploaded to a task, removing both the database record and the physical file from disk.

**Why:** Users currently have no way to remove files once uploaded. This creates several problems:
1. Mistakenly uploaded files (wrong file, duplicate, sensitive data accidentally attached) remain on the task permanently
2. Obsolete attachments (outdated versions, superseded files) continue to clutter the task and consume disk space
3. Users cannot correct upload errors without backend intervention
4. Storage costs accumulate as files cannot be cleaned up
5. Tasks with many attachments become difficult to navigate when old files cannot be removed

This is a standard CRUD completion gap. The attachment feature supports Create (POST upload), Read (GET list and download), but lacks Update and Delete operations. While Update may not be necessary for immutable files, Delete is essential for error correction and resource management.

## Current State vs. Desired State

### Current State (Files Cannot Be Removed Once Uploaded)

**AttachmentController Endpoints:**
- **Location:** c:/temp/KanbAI-Core/KanbAI-Core/KanbAI-Core/Controllers/AttachmentController.cs
- **Existing Endpoints:**
  - POST /api/attachment/task/{taskId} (lines 45-100) — Uploads a file, returns 201 with AssetResponseDto
  - GET /api/attachment/task/{taskId} (lines 102-162) — Lists all completed attachments for a task (added in issue #80)
  - GET /api/attachment/{assetId} (lines 164-241) — Downloads a file by asset ID, requires project membership authorization
- **Missing:** No DELETE endpoint exists. Once a file is uploaded and stored, there is no API method to remove it.

**Asset Entity & Storage:**
- **Location:** c:/temp/KanbAI-Core/KanbAI-Core/KanbAI-Core/Models/Entities/Asset.cs
- **Schema:** Asset has properties for FileName, StorageKey, MimeType, FileSize, ProcessingStatus, and a foreign key KanbanTaskId
- **Storage Location:** Physical files are stored in wwwroot/uploads/ with paths constructed from StorageKey (generated by AssetService during upload)
- **Current Behavior:** Assets remain in the database and on disk indefinitely until manually removed via database admin tools or file system access

**Path Resolution & Security (Established in GetFile Endpoint):**
- The GetFile endpoint (lines 205-219) implements path-traversal hardening:
  1. Resolves storage root from configuration (FileStorageOptions.StoragePath)
  2. Combines storage root with StorageKey (from database, not user input)
  3. Validates that the resolved path does not escape the storage root (lines 212-219)
  4. Logs warnings and returns 404 if path traversal is detected
  5. Logs warnings and returns 404 if the physical file is missing (orphaned DB record)
- This same pattern must be used for DELETE to ensure no user-controlled file paths

**Authorization Pattern (Established):**
- All AttachmentController endpoints require JWT authentication ([Authorize] attribute on controller, line 17)
- GetFile endpoint loads Asset → KanbanTask → BoardColumn → Project → Members (lines 171-177)
- Verifies the authenticated user is a member of the project before serving the file (lines 184-192)
- Non-members receive 403 Forbidden with structured error message
- The DELETE endpoint must follow the same authorization chain

**SignalR Broadcasting Pattern (Established in AssetService):**
- **Location:** c:/temp/KanbAI-Core/KanbAI-Core/KanbAI-Core/Services/Assets/AssetService.cs (line 184)
- When an asset completes processing, AssetService broadcasts "AssetCompleted" to the project's SignalR group
- Group name format: "project_{projectGuid.ToString().ToLowerInvariant()}" (from KanbanHub.cs line 43)
- Broadcast method: `_hubContext.Clients.Group(groupName).SendAsync("AssetCompleted", dto)`
- The DELETE endpoint must broadcast "AttachmentDeleted" using the same pattern so all connected clients can update their UI in real time

**ProcessingStatus Enum (Defined in Models/Enums/):**
- Pending: File is queued for processing
- Processing: File is being processed (e.g., thumbnail generation)
- Completed: File is ready for download
- Failed: Processing failed

### Desired State (Users Can Remove Attachments They No Longer Need)

**New Endpoint:**
- **Route:** DELETE /api/attachment/{assetId} (follows RESTful convention, parallels the existing GET /api/attachment/{assetId} pattern)
- **Parameters:**
  - assetId (Guid, from route) — The ID of the asset to delete
- **Authorization:** Requires JWT authentication (inherits from controller-level [Authorize] attribute)
- **Behavior:**
  1. Extract authenticated user ID via GetCurrentUserId() (existing helper method at line 243)
  2. Query the database to load the Asset with .Include(a => a.KanbanTask).ThenInclude(t => t.Column).ThenInclude(c => c.Project).ThenInclude(p => p.Members)
  3. Verify the asset exists (return 404 Not Found if not)
  4. Verify the authenticated user is a member of the asset's task's project (return 403 Forbidden if not)
  5. Resolve the physical file path using the same path-resolution and path-traversal hardening logic as GetFile (lines 205-219)
  6. Attempt to delete the physical file from disk:
     - If the file exists and deletion succeeds, proceed
     - If the file does not exist (orphaned DB record), log a warning and proceed (cleanup case)
     - If deletion fails (locked file, permission error), log an error, do NOT delete the DB row, return 500 with a generic error message (no filesystem details leaked)
  7. Delete the Asset row from the database
  8. Broadcast "AttachmentDeleted" event to the project's SignalR group with the asset ID so all connected clients can remove it from their UI
  9. Return 204 No Content on success

**Edge Cases & Error Handling:**
- **Asset in Pending/Processing state:** Still deletable — cancel/ignore the processing job and remove the record. Log at Information level.
- **Physical file missing (orphaned DB row):** Log warning, delete the DB row anyway, return 204 (cleanup case).
- **Disk delete fails (locked file, permission error):** Log error, do NOT delete the DB row (to avoid data inconsistency), return 500 with a generic message like "Failed to delete file. Please try again."
- **Non-project-member attempts deletion:** Return 403 Forbidden with structured error message, log at Warning level.
- **Asset does not exist:** Return 404 Not Found with structured error message, log at Information level.

**SignalR Broadcast:**
- **Event Name:** "AttachmentDeleted"
- **Payload:** Object containing { assetId: string, taskId: string } (both as string representations of Guids)
- **Group:** project_{projectId} where projectId is obtained from asset.KanbanTask.Column.ProjectId
- **Purpose:** Allow all connected clients viewing the same project to remove the deleted attachment from their UI in real time

**Security Considerations:**
- Authorization check must happen BEFORE attempting to delete the file or DB record (prevents unauthorized deletion)
- Path resolution must use the exact same hardening as GetFile (prevents path traversal attacks even if StorageKey is malformed)
- Error messages must not leak filesystem paths or sensitive server information (generic "Failed to delete file" on disk errors)
- Logging must use structured logging with proper log levels (Warning for authorization failures, Error for disk failures, Information for successful deletions)

**Logging:**
- Successful deletions logged at Information level: "User {UserId} deleted asset {AssetId} from task {TaskId}"
- Authorization failures logged at Warning level: "User {UserId} attempted to delete asset {AssetId} in project {ProjectId} without authorization"
- Asset not found logged at Information level: "User {UserId} attempted to delete non-existent asset {AssetId}"
- Orphaned DB record (file missing) logged at Warning level: "Asset {AssetId} physical file missing at {FilePath}, cleaning up DB record"
- Disk deletion failures logged at Error level: "Failed to delete physical file for asset {AssetId} at {FilePath}: {ErrorMessage}"

## Acceptance Criteria

### 1. Endpoint Exists and Accepts Correct Parameters
- [ ] DELETE endpoint is defined at route [HttpDelete("{assetId}")] (results in DELETE /api/attachment/{assetId})
- [ ] Endpoint accepts Guid assetId as a route parameter
- [ ] Endpoint signature includes CancellationToken cancellationToken parameter for graceful cancellation support

### 2. Authentication and Authorization
- [ ] Endpoint calls GetCurrentUserId() to extract the authenticated user's ID from the JWT token
- [ ] Endpoint queries the Asset with .Include(a => a.KanbanTask).ThenInclude(t => t.Column).ThenInclude(c => c.Project).ThenInclude(p => p.Members)
- [ ] If the asset does not exist, endpoint returns 404 Not Found with ApiResponse.Fail("File not found.")
- [ ] If the authenticated user is not a member of the asset's task's project, endpoint returns 403 Forbidden with ApiResponse.Fail("You are not authorized to delete this file.")

### 3. Path Resolution and Traversal Protection
- [ ] Endpoint resolves the physical file path using the same logic as GetFile: Path.Combine(storageRoot, asset.StorageKey) followed by Path.GetFullPath()
- [ ] Endpoint validates that the resolved path does not escape the storage root (same check as GetFile lines 212-219)
- [ ] If path traversal is detected, endpoint logs a warning and returns 404 Not Found (does not leak filesystem details)

### 4. Physical File Deletion
- [ ] Endpoint checks if the physical file exists using System.IO.File.Exists(resolvedPath)
- [ ] If the file exists, endpoint attempts to delete it using System.IO.File.Delete(resolvedPath)
- [ ] If the file does not exist (orphaned DB record), endpoint logs a warning at Warning level: "Asset {AssetId} physical file missing at {FilePath}, cleaning up DB record"
- [ ] If file deletion throws an exception (locked file, permission error), endpoint logs an error at Error level, does NOT delete the DB row, and returns 500 with ApiResponse.Fail("Failed to delete file. Please try again.")

### 5. Database Record Deletion
- [ ] If physical file deletion succeeds or the file does not exist, endpoint removes the Asset row from the database using _context.Assets.Remove(asset)
- [ ] Endpoint calls await _context.SaveChangesAsync(cancellationToken) to persist the deletion

### 6. SignalR Broadcasting
- [ ] Endpoint broadcasts "AttachmentDeleted" event to the project's SignalR group after successful deletion
- [ ] Event payload includes an object with assetId (string) and taskId (string)
- [ ] Group name is constructed as "project_{projectGuid.ToString().ToLowerInvariant()}" using asset.KanbanTask.Column.ProjectId
- [ ] Broadcast uses _hubContext.Clients.Group(groupName).SendAsync("AttachmentDeleted", payload)

### 7. Success Response
- [ ] Endpoint returns 204 No Content on successful deletion (no response body required for DELETE operations)

### 8. Edge Case: Pending or Processing Asset
- [ ] Assets with ProcessingStatus.Pending or ProcessingStatus.Processing can be deleted without special handling (deletion cancels the processing)
- [ ] Deletion of non-Completed assets is logged at Information level: "User {UserId} deleted asset {AssetId} with status {ProcessingStatus}"

### 9. Edge Case: Orphaned Database Record
- [ ] If the physical file does not exist but the database record does, the database record is still deleted (cleanup case)
- [ ] This case is logged at Warning level with structured logging: "Asset {AssetId} physical file missing at {FilePath}, cleaning up DB record"
- [ ] Returns 204 No Content (successful cleanup)

### 10. Edge Case: Disk Deletion Failure
- [ ] If File.Delete() throws an exception (file locked, permission denied), the exception is caught
- [ ] The database record is NOT deleted (to maintain data consistency and allow retry)
- [ ] Error is logged at Error level with structured logging: "Failed to delete physical file for asset {AssetId} at {FilePath}: {ErrorMessage}"
- [ ] Returns 500 Internal Server Error with ApiResponse.Fail("Failed to delete file. Please try again.") (no filesystem paths or details in response)

### 11. Error Responses
- [ ] 404 Not Found is returned when the asset does not exist
- [ ] 403 Forbidden is returned when the user is not a project member
- [ ] 500 Internal Server Error is returned when disk deletion fails (with generic message, no filesystem details)
- [ ] Error responses include ApiResponse.Fail(message) with a clear error message

### 12. Logging
- [ ] Successful deletions are logged at Information level: "User {UserId} deleted asset {AssetId} from task {TaskId}"
- [ ] Authorization failures are logged at Warning level: "User {UserId} attempted to delete asset {AssetId} in project {ProjectId} without authorization"
- [ ] Asset not found scenarios are logged at Information level: "User {UserId} attempted to delete non-existent asset {AssetId}"
- [ ] Orphaned DB records are logged at Warning level: "Asset {AssetId} physical file missing at {FilePath}, cleaning up DB record"
- [ ] Disk deletion failures are logged at Error level: "Failed to delete physical file for asset {AssetId} at {FilePath}: {ErrorMessage}"
- [ ] All logging uses structured logging (no string interpolation)

### 13. Security: Authorization Check Order
- [ ] Authorization check is performed BEFORE attempting to delete the physical file or database record (prevents unauthorized deletion attempts)
- [ ] Path traversal check is performed BEFORE attempting to delete the physical file (prevents attacks even if StorageKey is malformed)
- [ ] No filesystem paths or server details are leaked in error responses

### 14. Consistent with Existing Patterns
- [ ] Endpoint follows the same authorization pattern as GetFile (loading asset → task → column → project → members)
- [ ] Endpoint uses the same path resolution and path-traversal hardening as GetFile (lines 205-219)
- [ ] Endpoint uses the same GetCurrentUserId() helper method as other endpoints (line 243)
- [ ] Endpoint follows the same error handling pattern as other controllers (404 for not found, 403 for unauthorized, 500 for server errors)
- [ ] SignalR broadcasting follows the same pattern as AssetService.BroadcastAsync (group name construction, SendAsync call)

### 15. No Breaking Changes
- [ ] Adding this endpoint does not modify or break existing POST, GET list, or GET download endpoints
- [ ] The new endpoint is purely additive and does not change any existing behavior
