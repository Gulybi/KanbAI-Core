# Technical Specification: Issue #8 - Implement Base Entities and Standard API Responses

## Overview

Establish two foundational building blocks for all future domain modelling and API development:

1. **`BaseEntity`** — an abstract class providing identity and audit-timestamp columns that every EF Core entity inherits.
2. **`ApiResponse<T>`** — a generic response envelope that guarantees a uniform JSON contract for every API endpoint (success indicator, payload, error messages).

No concrete domain entities are introduced in this issue; no new EF Core migration is required.

---

## Database / Domain Design

### `BaseEntity` (abstract class)

| Property | Type | Purpose |
|---|---|---|
| `Id` | `Guid` | Unique primary key (client-generated by default via `Guid.NewGuid()`). |
| `CreatedAt` | `DateTimeOffset` | UTC timestamp set automatically when the entity is first persisted. |
| `UpdatedAt` | `DateTimeOffset` | UTC timestamp set automatically on every subsequent save. |

**Design Decisions:**

- **`Guid` over `int`:** Avoids sequential-ID exposure in URLs and is safe for future distributed scenarios (multi-node inserts, offline sync). Index fragmentation can be mitigated later with `newsequentialid()` column defaults if profiling shows a need.
- **`DateTimeOffset` over `DateTime`:** Preserves timezone offset; avoids ambiguous `DateTimeKind.Unspecified` bugs.
- **Auto-timestamping via `SaveChangesAsync` override:** Centralises audit logic inside `ApplicationDbContext` so individual entities never need to manage timestamps manually. Only the async path is overridden — synchronous `SaveChanges` is intentionally left unchanged because all I/O in this project must be async per `@rule_code_standards`.

**File:** `KanbAI-Core/KanbAI-Core/Models/Entities/BaseEntity.cs`
**Namespace:** `KanbAI_Core.Models.Entities`

```csharp
namespace KanbAI_Core.Models.Entities;

public abstract class BaseEntity
{
    public Guid Id { get; set; }
    public DateTimeOffset CreatedAt { get; set; }
    public DateTimeOffset UpdatedAt { get; set; }
}
```

### `ApplicationDbContext` changes

Override `SaveChangesAsync` to auto-populate `CreatedAt` / `UpdatedAt` on tracked `BaseEntity` descendants.

```csharp
public override Task<int> SaveChangesAsync(CancellationToken cancellationToken = default)
{
    foreach (var entry in ChangeTracker.Entries<BaseEntity>())
    {
        switch (entry.State)
        {
            case EntityState.Added:
                entry.Entity.CreatedAt = DateTimeOffset.UtcNow;
                entry.Entity.UpdatedAt = DateTimeOffset.UtcNow;
                break;
            case EntityState.Modified:
                entry.Entity.UpdatedAt = DateTimeOffset.UtcNow;
                break;
        }
    }

    return base.SaveChangesAsync(cancellationToken);
}
```

> **Note:** No `DbSet<>` properties or `OnModelCreating` configuration for `BaseEntity` itself — it is abstract. Concrete entities added in future issues will declare their own `DbSet<>` and inherit these columns automatically.

## API Contracts

### `ApiResponse` / `ApiResponse<T>` (response envelope)

Both types are C# `record` classes (per `@rule_code_standards` — records for DTOs / value objects).

| Property | Type | Description |
|---|---|---|
| `Success` | `bool` | `true` when the request completed without errors. |
| `Message` | `string?` | Optional human-readable message (e.g., `"Entity created successfully"`). |
| `Errors` | `IReadOnlyList<string>` | Collection of error descriptions; empty on success. |
| `Data` | `T?` | *(generic variant only)* The response payload. |

**File:** `KanbAI-Core/KanbAI-Core/DTOs/ApiResponse.cs`
**Namespace:** `KanbAI_Core.DTOs`

#### Non-generic base — for endpoints that return no payload (e.g., `DELETE`)

```csharp
namespace KanbAI_Core.DTOs;

public record ApiResponse
{
    public bool Success { get; init; }
    public string? Message { get; init; }
    public IReadOnlyList<string> Errors { get; init; } = [];

    public static ApiResponse Ok(string? message = null)
        => new() { Success = true, Message = message };

    public static ApiResponse Fail(string message)
        => new() { Success = false, Message = message };

    public static ApiResponse Fail(IEnumerable<string> errors)
        => new() { Success = false, Errors = errors.ToList().AsReadOnly() };
}
```

#### Generic variant — for endpoints that return data

```csharp
public record ApiResponse<T> : ApiResponse
{
    public T? Data { get; init; }

    public static ApiResponse<T> Ok(T data, string? message = null)
        => new() { Success = true, Data = data, Message = message };

    public new static ApiResponse<T> Fail(string message)
        => new() { Success = false, Message = message };

    public new static ApiResponse<T> Fail(IEnumerable<string> errors)
        => new() { Success = false, Errors = errors.ToList().AsReadOnly() };
}
```

**Design Decisions:**

- **`record` inheritance (`ApiResponse<T> : ApiResponse`):** Allows code that only needs to inspect success/errors to accept the non-generic base, while typed consumers get `Data`.
- **Static factory methods (`Ok` / `Fail`):** Enforce valid state construction — callers never manually set `Success = true` alongside an error list.
- **`IReadOnlyList<string>` for `Errors`:** Immutable once constructed; serialises cleanly to JSON arrays.
- **Pagination metadata deferred (YAGNI):** The acceptance criteria require data, success, and errors. Pagination (`PageNumber`, `PageSize`, `TotalCount`) can be added via a `PaginatedApiResponse<T> : ApiResponse<T>` subtype in a future issue when list endpoints are introduced.

### Example JSON shapes

**Success (with data):**

```json
{
  "success": true,
  "message": null,
  "errors": [],
  "data": [ { "date": "2026-04-07", "temperatureC": 25, "summary": "Warm" } ]
}
```

**Failure:**

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": [ "Name is required", "Email format is invalid" ],
  "data": null
}
```

## Application Layer Boundaries

No new services, MediatR handlers, or repositories are introduced in this issue. The two artefacts are strictly **domain infrastructure** (`BaseEntity`) and **API infrastructure** (`ApiResponse`).

Future issues will:
- Create concrete entities inheriting `BaseEntity` and register them as `DbSet<>` in `ApplicationDbContext`.
- Wrap all controller/minimal-API return values in `ApiResponse<T>`.
